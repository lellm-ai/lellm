实际 API 与迁移以 [可恢复执行](../docs/durable-execution.md) 为准，下文保留原始方案和验收拆分，未把拆分项创建为 Git 提交。主要收敛：

- 新运行使用显式字符串 run_id，与旧 trace_id 协议分离；保存调用身份和 revision，暂未增加独立 attempt_id。
- 新格式为 2；旧格式仍用旧入口完成，不提供通用 v1 导入器或业务状态自动迁移。
- 使用独立 content_token 绑定不可变审批快照，保存完整任务输入用于比较，不声称密码学摘要校验。
- 截止时间当前读取系统 UTC，测试使用明确到期边界；可注入时钟尚未交付。
- 新入口使用 validate_durable 放开已验收的组合；旧 validate_persistable 保持 format=1 限制。
- 全部审批/未知任务就绪后恢复，门槛作用于整个运行；暂不提供分支部分恢复 API。
- 收据和子帧全部保留，不提供 prune；保存完整信封的规模成本留待负载测量。
- 观察事件提供路径与提交 revision；durable 门面尚未暴露模型 token 流。
- 首个模板为固定 Planner → Workers → Reviewer；Supervisor、动态派工、更多模板未扩展。



用户确认的顺序：**审批可恢复 → 工具重放边界 → 子图和并行恢复 → 多 Agent 模板**。本文不预先分配发布版本；每阶段按验收条件交付。

## 2. 贯穿各阶段的执行契约

以下为初始设计契约，实际交付中的命名和范围差异见顶部说明。

1. **Graph 持有恢复协议。** Agent 负责工具与消息适配，Provider 负责模型调用；Graph 不依赖 Agent。ExecutableTool 继续留在 core，不负责调度。
2. **Engine 保持借用状态。** 持久化的是可重建的执行位置和结果，不是 Rust Future 或调用栈；不恢复已废弃的 ExecutionSession / FrameStack 旧系统。
3. **先同步持久化。** 暂停、决策接受、任务完成、父状态提交都有明确保存边界。保存失败立即停止，不执行后继节点。
4. **存储是恢复依据。** 展示事件可以丢失；审批查询和结果查询必须读存储。接收端断开不能隐式批准；新持久化入口默认允许执行继续到可持久化边界，显式取消单独处理。
5. **恢复保留身份与预算。** 使用现有 trace_id 作为逻辑运行身份；一次恢复另有 attempt_id，仅作观测。节点调用序号、工具身份、预算不会因重启重置。
6. **分开校验格式、状态与行为。** format_version 管格式，state_schema_version 管状态，workflow_version 管业务实现。结构 hash 是辅助检查，不能证明闭包或工具行为兼容。
7. **失败不等于回滚外部系统。** 已持久化结果可复用；外部成功但收据未保存仍有不确定窗口，按工具策略处理。

### 存储与兼容方案

- 新持久化入口引入独立的存储能力契约，要求「持有运行独占权时读取最新 revision 并提交新 revision」。当前 BlobCheckpointStore 不能仅通过先 load_latest 再 save 模拟原子操作。
- 首个文件后端限定本机文件系统，使用进程退出后自动释放的 OS 文件锁，持锁覆盖一次执行/恢复到暂停或结束；内存后端使用按运行隔离的锁。第二个执行者明确返回 Busy。暂停期间释放锁；提交决策与恢复都重新获取锁。
- 锁内仍校验 expected_revision；重复请求先按请求身份检查已接受的决策，再处理过期 revision。后续数据库后端可实现事务/CAS；分布式租约需要 fencing，另行设计。
- 推荐以完整恢复信封原子保存作为第一版：状态投影、执行位置、审批决策回执在同一次提交中可见。后续任务/分支收据可以独立存储，但父检查点必须引用确定的已提交记录，裁剪不得删掉活跃引用。
- 文件持久性沿用现有**进程崩溃恢复**保证。断电保证需要文件及目录同步和专项测试，单独交付。
- 当前 format_version=1 串行检查点继续由旧入口读取；新格式使用显式版本和严格字段检查。向新入口迁移 v1 必须显式补齐 workflow/schema 版本及身份，并通过校验；缺少游标字段不得推断为完成。
- 默认结构指纹应包含起止节点及有语义的边顺序；改变指纹算法也要版本化。业务逻辑、工具配置变化仍由 workflow_version 约束。首版不自动迁移业务状态。

## 3. M1：审批可恢复

### 交付场景

生成方案 → 保存待审批状态并返回 → 退出进程 → 新进程查询同一审批 → 提交决策 → 恢复后只推进一次。暂停不需要一直持有 Future 或消息通道。

### 数据与接口草案

| 数据 / 接口 | 职责 |
| --- | --- |
| RunPosition | Running / WaitingApproval / Completed / Cancelled 等可序列化位置；包含 next_node、调用序号、累计步数 |
| ApprovalRequest | approval_id、图路径、节点调用身份、审批内容及内容摘要、可选截止时间 |
| DecisionReceipt | 请求 ID、approval_id、所审批内容摘要、决策、接受的 revision |
| RunOutcome<S> | Completed(S) 或 Suspended(暂停引用)；执行错误沿用类型化错误返回，不把暂停伪装成成功 |
| start / inspect / submit_decision / resume | 泛型 Graph 恢复入口；Agent 只增加适配，SimpleExecutor 不成为唯一生产入口 |

身份使用 `(trace_id, graph_path, node_invocation, approval_slot)`，相关计数进入检查点；不使用 BarrierNode 共享 AtomicU32 作为持久化身份。审批绑定具体方案内容；工具参数或方案改变后必须生成新请求。

### 提交顺序

```text
节点完成 → 应用节点状态变更 → 保存 WaitingApproval + 请求 → 返回 Suspended
提交决策 → 获取独占权 → 校验请求/内容/revision → 保存决策回执 → 确认接受
恢复 → 获取独占权 → 读取最新状态与回执 → 应用决策并确定路由
     → 原子保存新状态、下一位置和决策已应用标记 → 执行后继
```

- 崩溃发生在决策保存后、应用前：恢复读取原回执；不会要求重新审批。应用中崩溃：从应用前快照重新计算；保存后崩溃：从后继继续。
- 相同请求与相同决策重试返回原回执；同一审批收到冲突决策明确拒绝。旧审批不能推进新的循环调用。
- 首个切片支持 Approve / Reject；Reject 保存终止结果，不进入工具节点。Modify / Reroute 在补齐可序列化输入、类型校验与幂等应用前显式拒绝。审批变更不能直接持久化任意 Mutation trait 对象。
- 截止时间存绝对时间；恢复时由可注入时钟判定。过期进入明确终止状态；取消与决策竞争在同一独占范围内确定顺序，取消不得被之后的决策复活。
- 新持久化模式缺审批能力时返回配置错误。现有非持久化入口静默批准的修正作为单独行为变更，提供显式 AutoApprove 选项与迁移说明。
- M1 只放开 Barrier 的持久化校验；Subgraph / Parallel 继续拒绝。子图现有静默审批缺口需要独立回归测试与入口校验，不能为了放开顶层 Barrier 而漏放嵌套组合。

### 拆分提交与验收

| 顺序 | 提交范围 | 必须通过的行为验证 |
| --- | --- | --- |
| A1 | 固化现有入口与能力矩阵，补审批缺配置回归用例 | 明确顶层/子图各入口行为；新模式未支持的组合执行前报错 |
| A2 | 新格式、严格 codec、身份与版本字段 | 损坏/缺字段/版本不兼容拒绝；v1 迁移不会误判完成 |
| A3 | 独占写入与 revision、内存/文件后端 | 两个执行者只有一个能推进；进程被杀后锁可重新获取 |
| A4 | Graph 持久化暂停与查询 | 保存暂停后杀进程；新进程仍查询到相同 ID 和内容；预算不重置 |
| A5 | 决策保存、去重、应用与恢复 | 同意/拒绝、重复/冲突/过期、取消竞争、各保存失败窗口；后继至多推进一次已提交位置 |
| A6 | Agent 适配、迁移示例与缺处理器行为修正 | Graph / Agent 同一审批契约；查询不依赖流事件；审批前工具调用计数为零 |

**M1 出口：** 使用真实子进程强制终止与新进程恢复完成上述主场景；并发提交不会绕过独占保护。此时才能宣称审批可恢复。

## 4. M2：工具重放边界

### 设计

Graph 提供通用任务收据协议，Agent 将每个工具调用映射为任务。稳定 task_id 由逻辑运行、图路径、节点调用、tool_call_id（不足以唯一时加调用槽位）构成；另存工具版本与参数摘要，重放时不一致立即报错。retry attempt 不参与幂等键。

工具执行上下文提供 task_id、idempotency_key 和取消信号。采用新增上下文调用入口并保留旧 execute(args) 的兼容适配；旧工具适配不自动获得安全重试保证。#[tool]、ToolFn 和 MCP 适配需分别覆盖。

| 策略 | 未找到完成收据时的处理 |
| --- | --- |
| ReadOnly / ReplaySafe | 允许重试；返回结果在持久化后固定复用 |
| IdempotentWithKey | 同一逻辑操作始终传相同幂等键，外部工具负责实际去重 |
| ManualRecovery（未声明时的推荐默认） | 对已开始但结果未知的调用暂停，等待对账或显式处置 |

ParallelSafety 只决定能否同时调用，不能代替上述重放策略。MCP 工具元数据也不能证明远端处理幂等键。

```text
保存 Planned(参数/身份) → 保存 Started → 外部调用
    → 保存 Completed(原始结果) → 处理结果并更新消息 → 保存节点检查点
```

- 恢复遇到 Completed：复用结果，不调用外部工具；tool result 消息、累计调用数和路由按同一 task_id 去重。
- 外部调用成功但 Completed 未保存：标记为结果未知，按策略重试或对账；Started 后尚未真正发出请求也可能保守地进入未知状态。
- ToolExecutor 的内部重试也遵守此协议，不能只在节点恢复层限制重放。结果后处理钩子要求纯函数/可重放；有副作用的钩子另成任务。
- 一个 ToolNode 内多个工具独立记录结果：A 完成且收据已保存、B 失败，恢复只处理 B。循环中再次调用同一个工具产生新的调用身份。
- 通用协议以后可包装 LLM 请求；本阶段不将未保存的模型响应视作可确定重放结果。节点末尾检查点以前的普通用户代码仍可能重跑。
- 收据裁剪与 checkpoint 引用关联；工具参数/结果可能敏感，复用已有受控存储，不无条件写入展示日志。

### 拆分提交与验收

| 顺序 | 提交范围 | 必须通过的行为验证 |
| --- | --- | --- |
| B1 | 通用任务身份、记录、版本校验与保留策略 | 恢复身份稳定，参数/工具版本不匹配拒绝；活跃收据不被 prune |
| B2 | core 工具上下文与旧 API 适配 | 手写工具、宏工具、MCP 均可用；旧工具保持可调用但不被误标为可重放 |
| B3 | ToolExecutor 重试与结果复用 | 同一次操作跨重试/重启幂等键相同；Completed 零外部调用 |
| B4 | ToolNode 批量结果与消息提交 | A 成功 B 失败，恢复 A 调用计数不增加；消息、预算不重复计入 |
| B5 | 未知结果对账入口与崩溃示例 | 完成前后每个崩溃窗口有确定处理；对账本身可重复提交且不重复推进 |

**M2 出口：** 文档能逐项解释每种工具在每个崩溃窗口是否重试、复用或暂停；测试证明这些行为，不以“支持 exactly-once”概括。

## 5. M3：子图和并行恢复

### M3a：先完成嵌套子图

- 使用稳定 namespace：父调用身份 + 子图节点名 + 调用序号；同一子图被重复/并行调用时互不覆盖。
- 显式保存父续接位置、子执行位置、子状态投影和累计预算。第一版沿用统一恢复信封保存嵌套记录，避免直接恢复旧 FrameStack API。
- 每种子状态由对应 SubgraphSpec 的类型化 codec 恢复，运行时信封只保存版本化载荷与路径。校验 StateLens 与 checkpoint projection 足以重建子状态；无法重建的 lens 在持久化入口拒绝。
- 子引擎继承持久化上下文、审批策略、取消和步骤追踪；事件携带完整路径。嵌套审批上传到顶层 Suspended，不能退回默认批准。
- 根运行定义全局步数上限，子图可以另设局部上限；保存两者已用值。计数口径需固定，恢复不得为子图重新分配全额预算。
- 子图完成后先保存完成结果，再把父状态和续接位置作为一次提交；父级提交前崩溃复用子结果，提交后崩溃不会二次应用。审批暂停保留子图中间快照，父级后继在子图完成前不执行。

### M3b：再完成显式并行节点

- 调度前保存固定分支集合、基准状态和 branch_id；成功分支的输出独立持久化。恢复复用成功分支，重启未完成分支；分支内部外部操作继续受 M2 约束。
- 第一版保留现有状态快照与 MergeStrategy，不先切换增量模型。合并顺序按持久化的分支顺序，不能依赖完成先后；自定义合并要求确定且无外部副作用。
- 全部分支成功后计算合并结果，父状态与下一位置原子提交。合并冲突返回明确错误，保留结果供检查；不得把部分成功状态混入父状态。
- FailFast 在首个错误到达时请求取消尚在运行的兄弟分支；已成功并保存的结果保留。协作取消未完成时保持执行权，不能启动重叠恢复；进程退出后的未知副作用按 M2 处理。
- CollectAll 等待全部分支并返回聚合错误。两者需要独立的测试与迁移说明，不能继续共用“join_all 后取首个错误”的名称承诺。
- 并行审批可以同时存在多个待决请求；允许分别接受决策，首版建议在该并行组所有待决请求就绪后再整体恢复。暂停前先让其他分支完成或到达可保存边界，不丢弃仍在执行的分支。

### 拆分提交与验收

| 顺序 | 提交范围 | 必须通过的行为验证 |
| --- | --- | --- |
| C1 | namespace、嵌套格式与类型化状态重建 | 同图多次调用身份隔离；不支持的 lens 启动前拒绝 |
| C2 | 子图能力传递与父子提交 | 两层子图审批重启可见；子完成/父提交之间崩溃无重复应用；预算与事件路径延续 |
| C3 | 分支记录、固定顺序与一次合并 | A 已保存 B 失败，恢复不重做 A；合并前后崩溃无重复父提交 |
| C4 | FailFast / CollectAll 与暂停、取消交互 | 错误到达即请求取消；聚合错误完整；取消尚未完成时不能启动第二执行者 |
| C5 | 组合验收与逐项放开校验 | 并行中子图审批、多个审批、任务收据复用、循环再次进入并行全部通过 |

**M3 出口：** 能用同一套运行身份、存储和决策接口恢复嵌套审批及部分完成的并行任务。只有对应验收通过后，才放开该组合的 validate_persistable 限制。

## 6. M4：多 Agent 模板

首个模板选择 Supervisor 或 Planner → Worker → Reviewer 的一个完整场景；每个 Agent 是已有 Graph 的组合。模板继承 M1–M3 的审批、工具策略、预算和恢复协议，不新增执行循环。

验收：Reviewer 审批期间重启；某 Worker 已完成、另一 Worker 失败时恢复；运行次数、工具外部调用数和父结果均符合 M1–M3 保证。通过后再扩充模板种类。

## 7. 测试与交付规则

- 用 fake 模型/工具、调用计数与 Notify/channel 确定失败窗口；不通过长 sleep 猜测保存完成。
- 跨进程测试沿用现有恢复测试思路：确认磁盘记录与可靠握手 → kill → 回收进程 → 新进程恢复。CheckpointSaved 展示事件不能充当可靠握手。
- 核心故障矩阵：保存前失败、保存后响应丢失、外部成功未保存、决策重复、执行权竞争、版本不兼容、完成态恢复、裁剪后恢复。
- 每个代码切片先测受影响 crate，再按仓库要求运行 workspace 全量测试；cargo fmt 与 diff 检查同时通过。单测 <10s，外部 IO/进程测试 <30s；>1s 标注原因。
- 每阶段同步公开 API 文档、可编译示例和迁移说明。新计划中的 checkbox 不能代替通过测试的交付证据。
- 正确性通过后再测检查点大小、写入次数、延迟和状态克隆开销；据此决定收据分离、批量写入或增量快照。Compiler InlinePass、Pregel 改造与分布式调度另立需求。

## 8. Grilling 决策树与下一轮评审

已确认根决策：恢复能力优先，按 M1 → M2 → M3 → M4 推进。用户随后授权全部依次继续，实施采用以下推荐边界；本轮未再引入审批停点。

| 当前决策 | 推荐答案 | 它决定的后续分支 |
| --- | --- | --- |
| 恢复的责任边界 | 框架负责稳定身份、收据复用、幂等键传递；工具负责外部幂等/对账 | 工具策略默认值、重试准入、未知结果处置 |
| 既有行为兼容 | 允许带迁移说明纠正静默批准与 FailFast；分开提交 | 旧入口默认值、弃用窗口、版本发布安排 |
| 首版存储部署范围 | 本机文件/内存后端强制单写者；共享数据库另实现事务契约 | 锁实现、分布式 fencing、跨主机恢复支持 |

后续架构评审聚焦审批修改/重路由、并行组部分恢复、跨版本迁移与大运行的存储成本。以上推荐是本轮实现选择，并不表示用户逐项回答了原始评审问题。
